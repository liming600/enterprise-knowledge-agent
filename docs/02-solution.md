# 02 方案设计

## 调用流程
1. HTTP 接收 question、history、mode；加载本地文档。
2. 真实模型每轮返回 JSON 动作、参数和简要依据。执行 search 或 read 后把实际返回结果加入消息，模型据此选择下一步或结束。
3. 执行层累计搜索候选与已读取原文；结束时拒绝未检索、未读取候选、无有效引用的回答。可回答时由执行层直接引用相关原文，不输出模型自由生成的事实；无相关资料返回 insufficient。
4. 执行层对相关原文中的同单位数字差异、允许/禁止表述和模型提出的冲突进行保守提示，并对多份适用关系不明的资料请求澄清。最多 8 步；耗尽后返回 incomplete。

工具为本地函数：search 返回 ID、标题、日期和片段；read 以逗号分隔 ID 读取原文。工具故障通过 fail 参数注入。Trace 为动作及观察摘要，不保存模型内部思维。

## 技术选择
采用 Python 标准库和兼容 Chat Completions 的 HTTP 接口，直接实现动作循环，没有引入 Agent 框架。这样减少安装步骤，便于查看模型决策、工具结果和停止条件；代价是超时、预算、参数校验等需要自行维护，也缺少框架提供的运行时能力。

检索使用文档分片、BM25、向量召回和 RRF 融合：关键词检索有利于匹配制度名称和明确术语，语义向量有助于处理改写，两者融合以兼顾不同问法。真实模式使用远程向量服务，离线或失败时降级为本地字符向量；后者便于复现流程，但不具备语义模型能力。没有引入向量数据库和重排序模型，降低部署复杂度，但大规模检索性能、召回率和排序效果仍待验证。

真实模式每次观察后请求模型决定下一步；Mock 使用固定流程，只验证流程与输出，不证明模型决策。为减少无依据回答，最终事实改为从已读取原文中摘录，而不是直接输出模型生成的事实；这提升引用可核对性，但不能保证检索片段一定适用或覆盖全部冲突。对于信息不足或多份资料关系不明的情况，选择明确返回缺口或请求澄清，代价是部分问题会得到较保守的答复。

## 边界
冲突规则覆盖有限的数字单位和允许/禁止表述，不具备通用语义矛盾检测。最终事实直接摘录原文，避免把模型自由生成的数字当成结论；这不能证明检索片段真正回答问题，相关性筛选与适用范围仍可能误判。检索阈值、分片及 top-k 可能遗漏资料；摘要仅保留用户问题且可能丢失细节，复杂指代仍需评测。默认本机监听，使用演示账号和 SQLite 持久化，不具备生产级安全保障。

## 访问控制与持久化

SQLite 保存用户、会话、文档、版本和用户记忆。登录令牌只在服务端以哈希保存；每次请求重新读取角色与部门。问答前先在服务端筛选公共与当前部门文档，再传给 Agent，模型和客户端无法指定额外文档。管理员可查看所有部门并管理版本；所有历史版本仅管理员可查看。上下文由当前会话的近期问题和旧问题摘要组成；用户可在聊天界面清除当前会话记忆和摘要，聊天记录保留。部门变更不会自动删除历史记忆。默认账号和本地 HTTP 仅适合演示。

批量管理扩展使用独立部门表与文档多对多授权表。归属部门用于分类，可访问部门用于过滤；公共授权对所有部门生效。导入、批量调岗及批量授权在同一事务中完成；既有文档的原部门会自动迁入授权表，迁移标记避免重复覆盖后续修改。

摘要采用最近 6 条及 3500 字节预算，旧问题由模型或截取式回退压缩；来源摘要和问题均为非证据。真实模型请求超过 48000 字节则返回 incomplete，不保证与供应商实际 Token 窗口完全匹配。授权过滤先于向量调用，语义向量和聊天模型各自使用配置的远程服务；模型不可用不会伪装成语义检索或模型摘要。

## 注入防护与预算

通过启发式规则识别常见的指令覆盖、角色伪造与泄密请求，过滤问题、记忆和摘要，在向量化前隔离可疑文档；工具动作采用白名单和参数校验，读取仅限授权且已检索文档。疑似注入及预算耗尽返回明确状态，不能证明对所有变形攻击免疫。每次请求共享 8 步、6 次工具、8 次模型（含摘要）、8 次向量请求和 120000 输入字节；相同动作及参数最多执行两次。120 秒为检查点和网络超时限制，可能因阻塞操作有偏差，详细限制见 README。
